## 1. Product and loop

Idle drone-racing strategy game. Every 3 minutes, every active drone is paired by level bracket and ELO and raced 1v1 by a deterministic simulator. A race is announced 3 minutes before it runs; the first 2 minutes are the strategy window (swap the equipped mod and skin, allocate stats), the last minute is locked. Winners earn Volts and XP, losers earn less of both. Volts buy stat upgrades, packs, capsules, vendor drones and marketplace items. Drones, skins and mods are on-chain tokens; a drone carries every item bound to it through a sale. AI racing teams own accounts, drones and Volts and play the same loop.

Loop: sign in (Google or Play Demo, 12) -> account and starter kit created on-chain -> allocate 20 stat points -> drone is active -> matchup appears -> swap loadout -> race settles on-chain -> Volts and XP arrive -> repeat.

### 2.10 AI teams (new)

4 teams. Per team: 3 drones (levels 4, 5, 8), 2 bound skins and 3 bound mods spread across them, 20,000 Volts. Caps: per transaction 5,000 Volts, per day 15,000 Volts, enforced on-chain on every Volt debit of a team account (`allocate_stats`, `buy`, `open_pack`, `vendor_buy_drone`); the day is `block_timestamp_ms / 86_400_000`; a team with no budget row has zero caps; regular players are never cap-checked. Reserve floor 5,000 Volts (the team never spends below it). All 3 drones are active (the 2.2 slot rule applies to players). Gas: a team account holds about 7 NEAR, sent from `hyperdrome.testnet`, and its play key has a 7 NEAR allowance (the seed starts a team at 2 NEAR and a 2 NEAR allowance, and the four teams were funded to these figures on 2026-11-09; a player has 0.05 NEAR and a 1 NEAR allowance), because a team sends a transaction on most ticks. ## 3. Architecture

Components: Next.js 16 app on Vercel (pages, API routes, scheduler endpoint hit every 3 minutes by Vercel cron or an external scheduler, AI-team runner inside the same tick); Neon Postgres (profiles, sessions, matchmaking inputs, caches of on-chain state, race logs); Pusher Channels (push to browsers); one NEAR contract `game.hyperdrome.testnet` (assets, Volts, economy rules, settlement, player account creation); NEAR testnet RPC (dRPC primary, FastNear failover; section 15).

Source of truth: ownership, balances, stats, level, XP, ELO, bound and equipped items, listings, batches, team budgets -> contract. Profiles, sessions, active flags, slots, matchmaking, race logs and snapshots, team personas -> database. The database caches on-chain fields and is refreshed from transaction outcomes and events; a nightly or on-demand `reconcile` view-read repairs drift.

Race cycle (one tick, slot S): (1) settle every committed batch of an earlier slot: read `get_batch`, snapshot each drone's locked on-chain state, simulate, `settle_batch` in chunks of 40, update caches from the events; (2) matchmaking from active drones the chain says are free, store the seed sealed, `commit_batch(S, hash(seed), matchups)`; (3) AI teams act on the committed matchups and their economy rules, one action per team (10). The tick is guarded by a unique `cron_ticks(slot)` row. Browsers read matchups and results by polling (9).

Trust boundaries: browser to server (session cookie, Zod, ownership); server to chain (per-player scoped keys, ops key, settlement key); server to AI teams (team scoped keys, on-chain caps); owner to contract (owner methods, upgrade key kept offline).

### 4.3 Standards

NEP-141 Volts: name "Volts", symbol "VOLT", decimals 0, icon none. `ft_transfer` standard (1 yocto). Storage registration is done by the contract for every player in `register_player` (contract pays).
NEP-171/177/178/181 via `NonFungibleToken`. `nft_transfer` and `nft_transfer_call` by hand: panic "bound item" if the token is a skin or mod with `bound_to`; if the token is a drone, transfer it, then `internal_transfer_unguarded` every bound skin and mod, clear approvals on all, emit one `NftTransfer` listing every moved token; panic "listed" if the token is listed; panic "locked" if `in_batch` is set and the batch is locked. `nft_token` returns metadata with `extra` = JSON summary (level, elo, tier, equipped). NFT collection metadata: spec `nft-1.0.0`, name "Hyperdrome", symbol "HDROME". `nft_metadata.base_uri` = the app's `/api/metadata`, set by the owner with `set_base_uri` (null until the app URL exists). Token `media` = `<base_uri>/<token_id>/image`, null while `base_uri` is null.

### 4.4 Methods

Owner (predecessor == owner_id):

- `create_player(slug: String, admin_pk: PublicKey, play_pk: PublicKey, is_team: bool) -> Promise`: creates `p-<slug>.<current>` (or `<slug>.<current>` when is_team) with CreateAccount, Transfer 0.05 NEAR, AddKey full-access admin_pk, AddKey function-call play_pk (receiver current, methods per 4.1, allowance 1 NEAR); then registers the player in a callback that returns true when the account was created. Panics "bad slug" if slug is not `[a-z0-9]{3,20}`, "exists" if the player is already registered.
- `register_player(account_id)`: FT storage registration and Player row; idempotent.
- `mint_drone(owner, name, level: u8, stats: [u8;9], active_hint: bool) -> TokenId`: validates level in 1-20 ("bad level"), each stat >= 1 ("bad stat") and <= cap(level) ("over cap"), sum <= TSB(level) ("tsb exceeded"); elo 1000; emits NftMint and `drone_minted`. `active_hint` is not stored (active flags live in the database).
- `mint_item(owner, kind, template: u16, placeholder_name: Option<String>) -> TokenId`: enforces skin supply caps unless placeholder or Ember ("no supply"; Ember is uncapped, 2.6, and still counted in `skin_minted`); a placeholder skin takes its rarity from `template` and is stored with template 0; "bad template" for an unknown template or a placeholder name on a mod; emits NftMint and `item_minted`.
- `mint_volts(to, amount)`: emits FtMint.
- `set_team_budget(account, per_tx, per_day)`; `set_paused(bool)`; `set_base_uri(base_uri: Option<String>)` sets `nft_metadata.base_uri`.
- `set_skin_caps(caps: [Option<u32>; 4])`: the per-template skin caps by rarity, in the order common, rare, epic, legendary; null is unlimited. Called with the owner's full-access key; it is not on the ops key's method list (4.1). Ember stays uncapped. A cap at or below a template's minted count stops further mints of it and changes nothing already minted. Fails with "not owner". Emits nothing.

Player (predecessor is a registered player, else "not player"; every method takes `seq: u64` which must equal `player.seq + 1`, then stores it; panics "bad seq" otherwise; panics "paused" when paused). Every Volt debit goes through one spend path: balance check ("insufficient volts"), then the team cap check if the caller is a team (2.10, "cap exceeded"), then the burn or payment. Methods on a drone check, in order: exists ("not found"), not listed ("listed"), caller owns it ("not owner"), not locked ("locked").

- `allocate_stats(drone, stats: [u8;9], seq)`: owner check; drone not locked; no decrease ("stat decrease"); each <= cap ("over cap"); sum <= TSB ("tsb exceeded"); cost per 2.1 burned (FtBurn, none when 0); team cap check if the caller is a team; adds the cost to `invested`; emits `stats_allocated`.
- `equip(drone, item: Option<TokenId>, kind, seq)`: owner check; drone not locked; `None` clears the slot; an item must exist and be of `kind` ("not found"), be bound to this drone ("not owner") and, for skins, pass the tier rule 2.6 ("tier"); emits `equipped`.
- `bind(drone, item, seq)`: owner owns both; item unbound; not listed; sets both sides; auto-equips if the slot is empty, the drone is not locked and (for skins) the 2.6 tier rule allows it; emits `item_bound`, plus `equipped` when it auto-equips.
- `list(token, price, seq)`: price >= 10 ("low price"); token exists ("not found"); not already listed ("listed"); owner check; not bound (for items, "bound item"); token and a drone's bound items move to contract escrow (internal transfer to current account, one NftTransfer; drone keeps racing and keeps `in_batch`); emits `listed`.
- `buy(token, seq)`: listing active ("not listed"); buyer != seller ("self buy"); Volts >= price; team cap check if buyer is a team; internal transfers buyer -> seller price - fee and buyer -> treasury fee, fee = floor(price / 10) (two FtTransfer); transfer token (and bound items) to buyer (one NftTransfer); remove listing; emits `sold`.
- `cancel(token, seq)`: listing active ("not listed"); seller check ("not owner"); token (and bound items) returns (NftTransfer); emits `cancelled`.
- `open_pack(kind, tier, hash: [u8;32], seq) -> u64`: tier 0 starter, 1 premium, 2 legendary ("bad tier" otherwise); price per 2.7 burned (FtBurn); team cap check; stores PackCommit with current height; returns the pack id (from 1); emits `pack_committed`.
- `reveal_pack(pack_id, secret: [u8;32], seq)`: pack exists ("not found"); buyer check ("not owner"); not yet revealed ("bad reveal"); `env::block_height() > height` ("too early"); `sha256(secret) == hash` ("bad reveal"); result = sha256(secret ++ env::random_seed() ++ pack_id LE bytes). Byte map for slot i in 0..3, all little-endian: rarity roll r_i = u32 at bytes [4i, 4i+4) / 2^32; template pick = u32 at bytes [12+4i, 16+4i); placeholder name pick = u16 at bytes [24+2i, 26+2i). Rarity per 2.7: the first entry whose cumulative bp exceeds floor(r_i * 10,000). Template = candidates[pick mod len], candidates in template id order: the rarity's skins with supply left, Ember excluded, or all mods of that rarity; with no skin left, a placeholder (template 0, name = pool[name pick mod pool len]). Mints the 3 items to the buyer (NftMint and `item_minted` each); marks revealed; emits `pack_opened` with the token ids.
- `vendor_buy_drone(seq) -> TokenId`: 3,500 Volts burned (FtBurn); team cap check if the caller is a team; seed = sha256(env::random_seed() ++ new token id UTF-8) (the chain seed is per block; the token id separates purchases in one block); a stream of u32 LE values, block k = sha256(seed ++ k as u32 LE), drawn in order: 9 stat rolls 1 + (u32 mod 5); while the sum exceeds TSB(1), one draw picks a stat above 1 (index = u32 mod count, in stat order) and lowers it by 1, at most sum - 29 steps; then skin pick, mod pick, placeholder name pick, name word, letter, digit. Name `WORD-<LETTER><DIGIT>` from the baseline `drone-names.js` word pool (not unique; the token id is the identity). One common skin (uniform among commons with supply left, Ember excluded, else a common placeholder) and one common mod (uniform among commons), both minted, bound and not equipped. Emits `drone_minted`, `item_minted` twice and `item_bound` twice, with their NftMint events.

Settlement (predecessor == current account):

- `commit_batch(batch_id: u64, seed_hash: [u8;32], matchups: Vec<Matchup>)`: predecessor == current account (near-sdk panics `Method commit_batch is private` otherwise). Panics `exists` if `batch_id` is stored; `not found` for an unknown drone, or a track, weather or time of day outside the 2.9 and 2.3 tables (settlement needs the track's difficulty); `locked` for a drone already in an unsettled batch or listed twice in `matchups` (a == b included). Listed (escrowed) drones may race. Sets `in_batch = batch_id` on every drone, stores the batch with committed_at_ms = block_timestamp_ms, settled false, settled_count 0; emits `batch_committed {batch_id, count}`.
- `settle_batch(batch_id: u64, seed: [u8;32], from: u32, results: Vec<RaceResult>)`: predecessor == current account. Settles races `from .. from + results.len()` of the batch (one chunk). Checks, in order: the batch exists (`not found`); `sha256(seed) == seed_hash` (`bad seed`); not settled, not aborted and from >= settled_count (`settled`); from == settled_count, from + results.len() <= matchups.len(), each result's (a, b) equals the matchup at its index, winner is a or b, both times > 0, the winner's time <= the loser's (equal times are the engine's tie-break, 2.4) (`bad chunk`); `stats_hash_a` and `stats_hash_b` equal the contract's current `stats_hash` of each drone (`state drift`). The result checks (`bad chunk` and `state drift`) run race by race, so within a chunk the first failing race decides which of the two is returned. Any failure reverts the whole call. Per race, from the pre-race levels and ELOs: payouts per 2.3 (difficulty from the track table, margin from the two times); ELO per 4.6; XP winner 10, loser 4; level-ups per 2.1 (while xp >= xp_to_next(level) and level < 20: subtract, level up, +20 Volts); wins and losses incremented; `in_batch` cleared on both drones. The Volts beneficiary of a drone is its owner; if the owner is the contract and a listing exists for the token, the listing's seller; otherwise (bots) nobody; an account not registered for Volts receives nothing (a drone moved by `nft_transfer` to an unregistered account cannot block settlement). Payouts and level-up Volts are minted with one aggregated nep141 `ft_mint` per call (one entry per beneficiary, summed, in order of first appearance; none when nothing is minted), followed by one `batch_settled` with the chunk's races, so a call logs 2 events whatever its size. settled_count += results.len(); settled becomes true when settled_count reaches the committed count, and the batch's `matchups` is then set to the empty Vec so its storage stake is refunded (a settled batch keeps seed_hash, committed_at_ms, settled and settled_count). The server attaches 200 TGas and settles a batch in chunks of 40 races with the same seed (13).
- `abort_batch(batch_id: u64)`: predecessor == current account. Panics `not found` for an unknown batch, `settled` if the batch is settled or already aborted. Otherwise, for every drone in the batch's matchups whose `in_batch` is this batch (a drone settled in an earlier chunk may already be in a later batch and is left alone), clears `in_batch`; sets `aborted = true`; empties `matchups`; pays and mints nothing; the batch's `settled` and `settled_count` keep their values. Emits `batch_aborted {batch_id, count}` with the number of drones unlocked. Recovery path for a batch whose seed is lost (the server cannot settle it, so its drones would stay locked for good).

Wallet (a player links one wallet it controls; DECISIONS.md 2.40):

- `link_wallet(player: AccountId, wallet: AccountId)`: owner only (ops key). Panics `not owner`, `not found` (unknown player), `team` (team accounts cannot link), `bad wallet` (the game account, the owner or any account under the game account), `linked` (a link exists; once linked, only `unlink_wallet` changes it). Registers the wallet for Volts if needed (contract pays, 13); emits `wallet_linked {player, wallet}`.
- `unlink_wallet(player: AccountId)`: exactly 1 yocto; caller must be the linked wallet. Panics `not linked`, `not owner`. Emits `wallet_unlinked {player, wallet}`.
- `withdraw(player: AccountId, tokens: Vec<TokenId>, volts: U128)`: caller is the owner (ops key, no deposit: `bad deposit` otherwise) or the linked wallet (exactly 1 yocto); any other caller `not owner`. Destination is always the linked wallet. Panics `not linked` with no link, `nothing to withdraw` with no tokens and 0 Volts, `too many tokens` when the tokens plus their bound items exceed the limit in 13. Per token, in order: `listed`; exists (`not found`); owned by `player` (`not owner`); a bound skin or mod alone is refused (`bound item`); a drone in a batch neither settled nor aborted (`locked`, from its commit on, stricter than the 120 s lock rule). A drone moves with every bound item through the existing transfer path (approvals cleared, one nep171 `nft_transfer` with `authorized_id` = the caller, per requested token). Volts move player to wallet (`insufficient volts`; `not registered` if the wallet removed its Volts registration with `storage_unregister`, which refunds its storage deposit, so the contract does not re-register it here); nep141 `ft_transfer` (the standard's log has no `authorized_id`). One `withdrawn {player, wallet, tokens, volts}`. Any failure reverts the whole call. Not gated by `paused`, like `nft_transfer` and `ft_transfer`.

`RaceResult { a, b, winner, time_a_ms: u32, time_b_ms: u32, stats_hash_a: [u8;32], stats_hash_b: [u8;32] }`.

Lock rule: a drone is locked when `in_batch` is set, the batch is neither settled nor aborted, and `block_timestamp_ms >= committed_at_ms + 120_000`.

### 4.5 Views

`get_constants()`, `get_player(account)`, `get_drone(token) -> {hot, cold, owner, listed, locked}`, `get_drones(tokens: Vec)`, `get_item(token)`, `get_items(tokens)`, `get_listing(token)`, `get_listings(from, limit)` (iterate via a `Vector<TokenId>` of active listings), `get_batch(id)` (seed_hash, committed_at_ms, matchups, settled, settled_count, aborted; `matchups` is `[]` once the batch is settled or aborted; a batch stored by the T6 build reads with `aborted: false`), `get_team(account)`, `get_catalog()` (skin templates with cap, null for Ember, and minted counts; mod templates), `stats_hash(token)` (same hash settle uses), `get_wallet_link(player) -> Option<AccountId>`, plus all standard `ft_*` and `nft_*` views.

### 4.6 Fixed-point ELO

`expected(d)` with d = ELO_l - ELO_w clamped to [-800, 800]: table `POW10[k]` = round(10^(k/400) * 1e6) for k = 0..800 step 25 (33 entries); interpolate linearly between entries; expected_w = 1e6 * 1e6 / (1e6 + pow10(d)) for d >= 0, and 1e6 - expected(-d) for d < 0; deltas = round(32 * (1e6 - expected_w) / 1e6) and round(32 * expected_w / 1e6) negated for the loser. The app displays what the contract stores.

### 4.7 Events (NEP-297, standard `hyperdrome`, version `1.0.0`)

`drone_minted {token, owner, level}`, `item_minted {token, owner, kind, template, rarity}`, `stats_allocated {drone, stats, cost}`, `equipped {drone, kind, item}`, `item_bound {drone, item}`, `listed {token, seller, price}`, `sold {token, seller, buyer, price, fee}`, `cancelled {token}`, `pack_committed {pack_id, buyer, kind, tier}`, `pack_opened {pack_id, tokens}`, `wallet_linked {player, wallet}`, `wallet_unlinked {player, wallet}`, `withdrawn {player, wallet, tokens, volts}`, `batch_committed {batch_id, count}`, `batch_aborted {batch_id, count}` (count = drones unlocked), `batch_settled {batch_id, races: [{i, a, b, winner, ta, tb, va, vb, elo_a, elo_b, xp_a, xp_b, lvl_a, lvl_b}]}` where `i` is the race's index in the batch, `ta`/`tb` the times in ms, `va`/`vb` the Volts minted for that drone in this race (payout plus 20 per level gained, 0 when nobody receives them; U128 strings), and `elo`, `xp`, `lvl` the drone's values after the race. One `batch_settled` per settle call, after its aggregated `ft_mint`. Snapshots are not in the event: the database stores them at settlement, before the call is sent (6), and the contract checks them through `stats_hash`. Standard nep141 and nep171 events on every mint, transfer and burn.

### 4.8 Errors

Panic messages are short lowercase strings and are the contract's API for failure paths: `paused`, `bad seq`, `not owner`, `not player`, `locked`, `bound item`, `listed`, `not listed`, `self buy`, `insufficient volts`, `over cap`, `cap exceeded`, `tsb exceeded`, `stat decrease`, `tier`, `bad slug`, `exists`, `state drift`, `bad reveal`, `too early`, `settled`, `bad seed`, `bad chunk`, `not found`, `same owner`, `bad level`, `bad stat`, `bad template`, `no supply`, `low price`, `bad tier`, `team`, `bad wallet`, `linked`, `not linked`, `bad deposit`, `nothing to withdraw`, `too many tokens`, `not registered`, `not migrated`. `over cap` is the per-stat cap (2.1); `cap exceeded` is a team spend cap (2.10); `low price` is a listing under 10 Volts; `bad tier` is an unknown pack tier; `bad seed` is a settle seed whose sha256 is not the committed hash; `bad chunk` is a settle chunk that skips ahead, overruns the batch, or has a result whose pair, winner or times do not fit its matchup (including a winner slower than the loser); `settled` is a settle or abort of a settled or aborted batch, or a settle of races already settled; `team`, `bad wallet`, `linked` and `not linked` are the 4.4 wallet rules; `bad deposit` is a deposit from the owner on `withdraw`; `not registered` is a Volt withdrawal to a wallet with no Volts registration; `not migrated` is a call on V1 state before `migrate` has run.

## 5. Engine (`lib/game-engine`, pure JS)

`simulateRace({ seed, raceId, droneA, droneB, track, weather, timeOfDay }) -> { winner: 'a'|'b', timeAms, timeBms, log }`. `seed` is the batch seed (hex), `raceId = "<batchId>:<index>"`; the race PRNG is xoshiro128** seeded with the first 16 bytes of sha256(seedBytes || utf8(raceId)), read as four little-endian u32 words (an all-zero state becomes 1, 2, 3, 4); `nextUnit()` = (next32() >>> 8) / 2^24. Draw order is exactly the baseline order: per lap, split straights (one draw per run except the last, which takes what is left), shuffle (Fisher-Yates), split turns, shuffle, start type; per segment: subtype pick, jitter, noise A, noise B; tie-break last, drawn only when the two millisecond totals are equal. `droneA/B` carry effective stats after mod application (`applyMod(stats, modTemplate)` in `lib/game-engine/mods.js`) and the special id; Phantom Drive and Storm Rider act in `scoreSegment`, Quantum Sync in the per-segment noise. `log` is client-safe: per segment `{lap, type, gapMs}` only, where `gapMs = Math.round((cumulative A - cumulative B) * 1000)` from the float sums (so the last `gapMs` can differ by 1 from `timeAms - timeBms`). Times are integers in milliseconds, computed from float seconds as `Math.round(t * 1000)` after the full sum so replay is byte-stable. `statsHash(stats9, modTemplateId, skinTemplateId)` in `lib/game-engine/stats-hash.js` mirrors the contract's `stats_hash` (sha256 of 9 stat bytes, u16 mod template LE, u16 skin template LE, 0 = none); `tests/golden/stats-hash.json` holds the shared test vectors. SHA-256 is a synchronous pure-JS implementation so replay runs the same in the browser. Mod templates live in `lib/game-engine/templates.js`, a mirror of the contract's `constants/catalog.rs` checked by a test.

## 6. Server and chain adapter (`lib/near`)

near-api-js 7.4.0, Node 22+. Nothing outside `lib/near` imports it (ESLint `hyperdrome/near-boundary`). Files: `config.js` (env, Zod), `provider.js`, `keys.js`, `events.js`, `errors.js`, `explorer.js`, `adapter.js` (real), `play-key.js` (the play key's scope and the rotation's actions), `mock.js` (in-memory, same interface), `index.js` (`getNear()` returns the process singleton; `NEAR_ADAPTER=mock` selects the mock). Interface (JSDoc types in `index.js`); every call returns `{ txHash, result, events }`, `events` being the parsed `EVENT_JSON` logs in receipt order:

- `createPlayerAccount({ slug, isTeam, onSigned }) -> { accountId, playKeyEnc, adminKeyEnc, keyVersion: 1, txHash }`: generates both ed25519 keypairs locally, calls `create_player` with the ops key (60 TGas), returns the keys sealed for storage. `AccountCreateError` if the callback returns false. On `RpcUnknownOutcomeError` the sealed keys are on `err.pending`, so the caller can store them before resolving. `onSigned({ accountId, playKeyEnc, adminKeyEnc, keyVersion, txHash })`, when given, is awaited after signing and before the broadcast, and nothing is sent if it throws; the team seed (10) stores the keys there, because a team's account name can be created only once.
- `callAsPlayer(accountId, playKeyEnc, method, args, { gas = 30 TGas })`: opens the play key, reads `get_player(account).seq` and sends `seq + 1` in the args; `{ seq }` in the options pins the seq instead (the action path pins one seq per action, 8); `{ onSigned(txHash) }` is awaited after signing and before the broadcast, and if it throws nothing is sent (the action path stores the hash there, 8).
- `callAsOps(method, args, { gas = 30 TGas, onSigned })` (signed by `NEAR_OWNER_ID` with `NEAR_OPS_KEY`; `onSigned(txHash)` runs after signing and before the broadcast, 8); `callAsSettlement(method, args, { gas = 200 TGas })` (signed by `NEAR_GAME_ID` with `NEAR_SETTLEMENT_KEY`).
- `view(method, args)` (optimistic finality; if every provider fails, one more failover round; contract panics are not retried); `getConstants()` cached per process.
- `nextSeq(accountId)`: the seq the next player call carries (`get_player(...).seq + 1`); panics `not player` when unregistered.
- `resolveOutcome(accountId, seq, txHash, { senderId = accountId })`: after `RpcUnknownOutcomeError`, if the on-chain seq reached `seq`, fetches the transaction by hash (looked up under `senderId`, the signer: the owner for `create_player`) and returns `{ applied: true, txHash, result, events }`; otherwise (or if that transaction failed with `bad seq`) `{ applied: false }`, so the caller may retry.
- `rotatePlayKey(accountId, adminKeyEnc, { keyVersion, allowance }) -> { playKeyEnc, keyVersion: keyVersion + 1, txHash }`: the only code path that opens an admin key; one transaction signed with it: DeleteKey for every function-call key scoped to the game contract, AddKey for a new play key (methods per 4.1; `allowance` in yoctoNEAR, 1 NEAR when omitted, 2 NEAR for AI teams, 2.10).
- `accountBalance(accountId) -> bigint`: the account's NEAR balance in yoctoNEAR (`view_account`, optimistic finality). The team seed (10) reads it to see the gas transfer arrive; the mock reports what `mock.setBalance(accountId, yocto)` set.
- `fundingStatus(teamAccounts) -> { settlementAllowance, opsAllowance, gameBalance, gameAvailable, lowestTeamBalance, lowestTeamAllowance }`: yoctoNEAR left on the settlement and ops keys (null when unlimited), the game account's balance, that balance above its storage stake, and the smallest balance and play-key allowance among `teamAccounts` (`lib/near/funding.js`; read-only).
- `transactionEvents(txHash, { senderId = gameId }) -> events | null`: read-only, no key opened and nothing sent; the parsed events of a finished transaction by hash (`tx` with `wait_until: NONE`, looked up under `senderId`, the signer; the game account signs settlement calls). Null when the RPC does not know the hash or the transaction has not reached `EXECUTED`; a failed transaction throws as a failed call does. It asks with `NONE` because a `tx` read that waits for `EXECUTED` on an unknown hash ends in the RPC's timeout, not in `UNKNOWN_TRANSACTION` (seen on both testnet RPCs, 2026-11-05). The rewards backfill (7) reads settle transactions with it; the mock answers from the calls it ran.
- `verifyWalletSignature({ accountId, publicKey, signature, message, nonce, recipient, callbackUrl }) -> Promise<boolean>` (`lib/near/wallet-signature.js`): near-api-js 7.4.0 `verifyMessage` (NEP-413) with the public key checked as a full-access key of `accountId` on chain (`viewAccessKey`); `signature` is the NEP's base64 string and `nonce` 32 bytes. False for a signature or key that does not hold up; RPC failures throw. The mock answers from `mock.setAccessKey(accountId, publicKey, permission)`.
- `explorerTx(hash)` = `<explorer>/txns/<hash>`, `explorerAccount(id)` = `<explorer>/address/<id>`; `ownerId` and `gameId` are the configured accounts.
- Mock (`mock.js`): `mock.failNextSend('applied' | 'lost')` makes the next create, ops, settlement or player send end in `RpcUnknownOutcomeError` (a create carries `err.pending`); `mock.on(method, handler)` supplies results, events and views. Settlement runs on an in-memory chain (`mock-chain.js`, `mock.chain`: drones, items, batches, Volt balances) with the contract's rules for `commit_batch` (`exists`, `not found`, `locked`), `settle_batch` (`not found`, `bad seed`, `settled`, `bad chunk`, `state drift`; payouts, XP, level-ups, ELO, one aggregated `ft_mint`, one `batch_settled`) and `abort_batch`, and the views `get_drone(s)`, `get_item(s)`, `get_batch`, `stats_hash`, `ft_balance_of`; a handler set with `mock.on` takes precedence.
- `sealSecret(bytes, keyHex, aad)`, `openSecret(blob, keyHex, aad)`: AES-256-GCM, 12-byte IV, 16-byte tag, key = 64 hex chars; blob = base64(version byte 1 ++ IV ++ tag ++ ciphertext); AAD = the row it belongs to (the account id for keys). Play keys under `KEY_ENCRYPTION_KEY`, admin keys under `ADMIN_KEY_ENCRYPTION_KEY`; `key_version` on the row. Also used for batch seeds.
- Sending: transactions are built and signed in the adapter (hash known before sending), sent with `waitUntil: 'EXECUTED'` (the transaction's block is final and every non-refund receipt has executed), deposit always 0. After a send timeout, or an InvalidNonce (after a failover the second node usually rejects the same signed transaction because the first already executed it), the adapter looks the transaction up by hash (3 attempts) and returns that outcome; it raises `RpcUnknownOutcomeError` or `NonceError` only when the hash is unknown. Ops and settlement calls carry no seq, so this is what stops a rebuilt resend from applying twice. An ops or settlement call that still ends in `NonceError` (another process used the key, such as a command-line call) is rebuilt with a fresh nonce and sent once more, so a manual use of either key never costs a player a failed request. A call with `onSigned` is never rebuilt: its lookups may have failed without proving the first send did not execute, and the caller resolves it from the stored hash (8).
- Errors (`errors.js`): `ContractPanicError` (`panic` = the 4.8 string, `method`, `txHash`), `KeyAllowanceError` (NotEnoughAllowance), `NonceError` (InvalidNonce; ops and settlement reset their nonce cache and resend once), `RpcUnknownOutcomeError` (`txHash`, `accountId`, `seq`), `AccountCreateError`, `TransactionFailedError` (a non-panic failure). Other errors propagate unchanged. Logging is `console.error({ scope: 'near', msg, ...fields })` only.
- RPC: near-api-js `FailoverRpcProvider` over `NEAR_RPC_URL` then `NEAR_RPC_FAILOVER_URL` (defaults in 15), each call raced against a 10 s timeout (near-api-js has none), 2 retries inside a provider. `NEAR_RPC_API_KEY`, when set, is sent as `Authorization: Bearer` to whichever URL is FastNear.
  Scheduler (`services/scheduler.service.js` `runTick`, behind `/api/races/run`): slot = floor(unix_seconds / 180). The route checks `CRON_SECRET` in constant time, as `Authorization: Bearer <secret>` (Vercel cron) or `x-cron-secret: <secret>` (an external scheduler or `scripts/tick.mjs`); `vercel.json` ships `crons: []`; production is driven by a cron-job.org job that calls `/api/races/run?mode=background` every minute (`docs/runbooks/deploy.md`, DECISIONS.md 5.47). A tick claims `cron_ticks(slot)` with INSERT ... ON CONFLICT DO NOTHING and exits (`claimed: false`) when the row exists. `beginTick` makes the claim and returns the phases; `runTick` runs them at once (the default, used by `scripts/tick.mjs` and the smoke); `?mode=background` answers before they run (8). Phases in order: phase 1 settle, phase 2 commit, phase 3 teams: `runTeamPhase({ slot, matchups, deadlineMs })` (10) with the matchups `commit_batch` took (none when no batch was committed or its commit did not stand) and `deadlineMs` = tick start + 40 s on the wall clock (the route allows 60 s). A team phase that throws is logged and reported in the tick's answer (`teams: { error }`); the tick stands. When `admin_config.racing_enabled` is not `true` the tick still settles due batches, so no drone stays locked, commits nothing and runs no team phase. Every chain call is idempotent by `batch_id`; a failed phase leaves the batch in its state and the next tick resumes it.
  Commit (`services/batch.service.js`): candidates are DB `drones.active` player drones with a token id, kept when on-chain `in_batch == null` and, for player drones, the chain owner is the cached player's account (a listed drone is in escrow and keeps racing) (`get_drones`, 50 per call). A drone whose owner is otherwise (withdrawn straight from the wallet) is not committed and its row, with its bound items, is synced from the nep171 event path (`user_id` null, inactive). A wallet withdrawal that lands between this read and `commit_batch` still races once, and its Volts go to the wallet (the owner, 4.4 settlement). Brackets, ELO pairing and the same-owner rule are `lib/game-engine/matchmaking.js` (pure). Bots are contract-owned drones in the cache (`is_bot`, seeded by T13), least-raced first, filling each non-empty bracket per 2.3; none are created, and with none seeded a bracket races without bots. Per matchup: a track drawn uniformly from the 2.9 set for the drone's level (`lib/game-engine/tracks.js`, a mirror of the contract's table checked by a test, matched to the `tracks` row by name), weather and time of day uniform (2.3), all from `crypto.randomInt`. Seed: 32 bytes from `crypto.randomBytes`. Before any chain call the batch row is written (slot, seed_hash, seed_enc sealed under `KEY_ENCRYPTION_KEY` with AAD = the slot as a string, status `committed`, attempts 0) with the races rows (batch_slot, race_index, drone ids, track, weather, time of day, elo_before from the cache, status `pending`) and the cached lock (`drones.in_batch`). Then `commit_batch(slot, seed_hash, matchups)` with `callAsSettlement`; `commit_tx` and `committed_at` are stored. `exists` means an earlier send landed: `get_batch(slot)` must carry this seed hash, then the commit stands (without a hash). Any other panic (`locked`, `not found`) fails the batch and its races and clears the cached lock. An unknown outcome leaves the row `committed` without `commit_tx`. No matchups: no batch row.
  Settle (`services/settle.service.js`, writes in `settle-store.js`). First, late commits: every batch with status `failed`, no entry in `settle_txs` and a slot within the last 480 slots (24 hours; a NEAR transaction is valid for 86,400 blocks), newest first and at most 20 per tick, is read with `get_batch`; one that is on chain with the row's seed hash, neither settled nor aborted (its commit landed after the database failed it), is aborted with `abort_batch`, the transaction hash stored in `settle_txs` and the events applied, so its drones unlock. Then, for every batch with status `committed` and slot < the current slot: read `get_batch` first. No batch on chain: failed once it has a `commit_tx` or is a full cadence old (the commit never landed), else left for the next tick. Chain aborted: failed. Chain settled: finished locally. Otherwise the seed is opened and every unsettled race's drones are read with `get_drones` and `get_items`; the snapshot `{ stats, modTemplate, skinTemplate, level, elo }` is the post-lock state the race runs with and is stored on the race row with the computed result before anything is sent. Each race runs `simulateRace` with the seed hex, raceId `<slot>:<index>`, `raceDrone(stats, modTemplate)`, the stored `tracks` row, weather and time of day; results carry `statsHash` of the snapshot. Chunks of 40 from the chain's `settled_count` go through `callAsSettlement` (200 TGas); each transaction hash is appended to `settle_txs`, the chunk's races become `completed` with `settle_tx`, and the events go through `applyEvents` (8), which also writes each race row's rewards from `batch_settled` (7). When the last chunk settles the batch is `settled` and the seed is stored plain on the batch and its races (`seed_enc` cleared). A refused or failed `settle_batch` (`state drift`, `bad chunk`, `bad seed`, a non-panic failure) adds 1 to `batches.attempts` and the next tick re-reads the chain and recomputes; the third failure calls `abort_batch` in the same tick (its hash appended to `settle_txs`), marks the batch and its pending races `failed` and logs it (drones unlock, nothing is paid). `settled` from `settle_batch` and an unknown outcome are not attempts: the next tick reads `settled_count` and sends only the rest. Races the chain settled while the outcome was unknown are completed from their stored snapshots (no `settle_tx`), with the drones' hot state and the owners' balances re-read; no event reaches them, so their reward columns keep the defaults (7).
  World seed (`services/world-seed.service.js`, run by `scripts/seed-world.mjs` as `npm run seed:world`, which reads `.env.local` through `node --env-file`): four steps, each reading what exists before it writes, so a second run changes nothing and a stopped run resumes. (1) Tracks: the 16 rows of `lib/game-engine/tracks.js` in `tracks`, matched by name; a missing row is inserted and a row whose straights, turns, difficulty, level range or length differ is corrected in place (its id stays). (2) `admin_config`: the one row the app reads, `racing_enabled`, created `false`; `--racing-on` sets it `true`; the seed never sets it `false`. This step is written last, after the bots and the catalog, so racing is never switched on over a roster a stopped run left incomplete. (3) Bots (2.3): the chain is the source of truth. A bot is a drone the game account owns that is not listed (`nft_supply_for_owner(NEAR_GAME_ID)`, then `nft_tokens_for_owner` in pages of 50 while tokens remain, since the standard panics on a `from_index` at or past the end, then `get_drones`; a listing in escrow has `listed: true`). Each bracket is topped up to 5 with `mint_drone(owner = NEAR_GAME_ID, name, level, stats, active_hint: true)` through `callAsOps`, and every bot on chain without a `drones` row gets one from its view (`is_bot` true, no user, active). Brackets are counted by the bots' current levels: bots earn XP, so once a bot has levelled out of its bracket a later run mints its replacement there. A bot whose cache row belongs to a user stops the seed (the database caches another deployment of the contract). (4) Catalog cache: `get_catalog()` into `catalog_templates` (7) through `services/catalog.service.js` `syncCatalog`: one row per skin template (name from the app's mirror, rarity, image path, `cap`, null for Ember) and per mod template (name, rarity, bonus, penalty, special; `cap` null); a changed row is updated. Minted counts are not cached. The script prints the explorer link of each mint as it lands and one line per step (created, updated, skipped). It needs the real adapter. A mint whose outcome is unknown stops the run; the next run reads the chain first.

The four testnet teams were first seeded with an earlier kit and brought up to this one with `--reconcile`; binds are permanent, so each also keeps an Ember on its level 4 drone, Hairpin a Rain Shield and Static a Night Lens on their level 8 drones.

Persona allocation (`allocateAlongPersona` in `lib/teams/allocation.js`): points are added one at a time. Each point goes to the stat furthest below its share, where a stat's share is `weight / 100 * (TSB(L) - 9)` points above 1; ties go to the larger weight, then to 2.1 order. A stat at cap(L) is skipped, and so is a point whose cost (2.1) no longer fits the Volt budget. It stops at TSB(L) or when no point fits. The seed runs it with no Volt budget (minting costs no Volts), the runner with the team's spare Volts.

Fit score (`lib/game-engine/mod-fit.js`, pure): for a race, mix = straights / (straights + turns) of its track. w(stat) = mix \* straightWeight(stat) + (1 - mix) \* turnWeight(stat), with straightWeight from `standard_str` (speed 0.5, acceleration 0.3, wind_resistance 0.2) and turnWeight from `standard_turn` (turning 0.5, durability 0.3, acceleration 0.2) in 2.4 and 0 for every other stat, plus 0.5 for rain_handling when the weather is rain or heavy_rain, for night_vision when the time is night or the weather is fog or haze, and for wind_resistance when the weather is wind. fit(mod) = bonusPct \* w(bonusStat) - penaltyPct \* w(penaltyStat). A legendary mod scores its special in place of the bonus term: Phantom Drive 2 always, Quantum Sync 2 when mix < 0.5, Storm Rider 3 when a condition weight applies; each minus its penalty term. Scores are rounded to 6 decimals. A fit can be exactly 0: Night Lens, Night Optics and Predator Lens in a race that tests neither of their stats, and Streamline Plate and Aero Shell at mix 1/3 (Voltage Loop). Each step below states how it breaks ties.

Seeding (`npm run seed:teams`: `scripts/seed-teams.mjs`, `services/team-seed.service.js`, `services/team-seed-kit.js`; runbook `docs/runbooks/seed-teams.md`): idempotent, with progress in `users.bootstrap_state`. `none -> account`: `createPlayerAccount({ slug, isTeam: true, onSigned })`; the sealed keys and hash of every attempt are stored in `bootstrap_pending` before the broadcast, so a create that lands while its answer is lost, the process dies or a write fails is found by `resolveOutcome` on the next run (an attempt that executed and failed is dropped). `account -> minted`: `set_team_budget` with the 2.10 caps, then with the ops key the 3 drones, 2 skins and 3 mods, and `mint_volts` up to 20,000. Mints cannot be undone, so `bootstrap_pending` now holds a mint ledger: each piece's token id is written as its mint returns, a token the chain already shows is adopted, and a mint with an unknown outcome is stored with its hash and resolved before anything else is minted (a transaction the RPC still does not know after 10 minutes counts as dropped). `minted -> done`: `bind` with the team's play key for every ledger item not yet bound to its drone; the cache rows are rebuilt from chain views through `applyEvents` (8), only once the views show the whole kit bound, and the 3 drones set active; the `teams` row is written; then gas. When the account holds under 2 NEAR the script prints the near-cli-rs command that sends 2 NEAR from `hyperdrome.testnet` (signed with the full-access key on the command line, never by application code) and waits until `accountBalance` shows it; when `hyperdrome.testnet` holds under 10 NEAR it stops before asking. Then `rotatePlayKey` with a 2 NEAR allowance; `key_version` 2 marks funding and rotation done. A team that is `done` is skipped with no chain call. `npm run seed:teams -- --reconcile` is for a roster change: for a team that is `done` it mints and binds the roster's drones, skins and mods the team does not have yet through the same steps, and never mints Volts, sends gas or rotates the key.

Team phase (`services/teams.service.js` `runTeamPhase({ slot, matchups, deadlineMs })`): the scheduler calls it after it commits the batch for `slot`, with the committed matchups (4.2 `Matchup`). Teams act in account order, starting at index `slot mod count`, so the same team is not always last; a team whose turn would start when `Date.now() > deadlineMs` is skipped. Each team takes at most one chain action per tick: the first of the steps below that applies (`decide` in `lib/teams/policy.js`). Volts come from `ft_balance_of` and the caps from `get_team`, everything else from the cache. Spare Volts = Volts - reserve, and no action plans more than the per-transaction cap or what is left of the day's cap (`per_day - spent`, with `spent` counted only on the contract day it was spent).

- (a) equip: for each team drone in the committed matchups, in matchup order, the bound mod with the best fit for that race (ties: the equipped mod, then the lower token number); `equip` it when it is not the equipped one.
- (b) bind: an unbound, unlisted mod the team holds whose fit for one of its racing drones beats that drone's best bound mod (0 with none bound) is bound to that drone (`bind`, permanent). The largest gain wins (ties: the lower mod token number, then the earlier matchup). Equipping it is step (a) on a later tick; the contract equips it at once when the drone's mod slot is empty (4.4).
- (c) allocate: the first drone (highest level first) with TSB headroom gets every point the spare Volts pay for, along the persona weights (`allocate_stats`).
- (d) capsule: when spare Volts >= the starter capsule price and the team holds fewer than 6 unbound mods (its own listings count), open a starter mod capsule; a premium one when spare Volts >= 20,000 and its price fits the caps. A premium capsule costs 6,000 and the 2.10 cap is 5,000, so today teams open starter capsules only.
- (e) list: when the team holds 3 or more unbound, unlisted mods and has a drone in the matchups, list the mod whose best fit across the team's races this tick is lowest (ties: the cheaper rarity, then the lower token number) at 1.2x its rarity base price (common 150, rare 800, epic 3,500, legendary 12,000). Only unbound mods are listed, never a bound one.
- (f) buy: an active mod listing of another seller whose fit for one of the team's racing drones beats that drone's best bound mod (0 with none bound) by 2 or more, priced at or under 0.8x its rarity base, within the spare Volts and the caps. The largest gain wins (ties: the lower price, then the lower token number).

Every action goes through `runPlayerAction` (8) with `actionId` = the version 5 uuid of `<team slug>:<slot>:<step>:<subject>` in the namespace uuid v5(DNS namespace, `teams.hyperdrome`) (`lib/teams/action-id.js`). The subject is the drone token (equip, allocate), the capsule tier, or the mod token (bind, list, buy). A capsule goes through the pack service (8) under that id. Before deciding, the runner reads the team's latest action. When that action carries this slot's id (the tick ran before), or is unfinished (its outcome is unknown, or it is a capsule committed and not yet revealed), it is sent again under its own id, so it replays or resolves and nothing new is sent; that is the team's action for the tick. Any answer other than applied or pending (`cap exceeded`, `insufficient volts`, any other refusal) ends the team's turn, and the next tick decides again; a plan equal to the team's latest action, when that action was refused, is passed over for the next step, so one refusal cannot repeat every tick. On-chain caps are the hard limit.

Tests (`tests/engine/mod-fit.test.js`, `tests/teams/`): fit vectors, persona allocation and action ids as pure tests; the seed and the runner against the mock adapter and a real Postgres.

A request first claims a 120 s lease (longer than the route's 60 s `maxDuration`) (`bootstrap_claimed_at`, conditional UPDATE), so two requests never act at once; each transition is `UPDATE ... WHERE bootstrap_state = <expected>`. Steps, each idempotent and resumable:

1. `none -> account`: resolve every stored `bootstrap_pending` attempt with `resolveOutcome(accountId, 0, txHash, { senderId: owner })` and adopt the first that executed and returned true; an attempt that executed and failed (a panic such as `exists` when another player took the slug, a non-panic failure, or a false callback) is dropped from `bootstrap_pending`; otherwise `createPlayerAccount({ slug, isTeam: false })` with the slug from the username (`[a-z0-9]{3,20}`: lowercase letters and digits, first 20, `pilot` in front when fewer than 3), a 4-hex suffix on `exists` or a false callback (base cut to 16, 5 attempts). On `RpcUnknownOutcomeError` the sealed keys go to `bootstrap_pending` and the state stays `none`.
2. `account -> minted`: read `nft_tokens_for_owner` and adopt tokens already owned; then with the ops key, only what is missing: `mint_drone` (all stats 1, level 1, name from `drone-names`), `mint_item` Ember (skin template 4), `mint_item` one common mod (template 1-10 from `crypto.randomInt`), `mint_volts` up to 1,000 (`ft_balance_of` first). Each token id is written to its drones, skins or mods cache row as it is minted.
3. `minted -> done`: `bind` the skin and the mod with the player's play key where `get_drone` shows them unbound (bind auto-equips an empty slot, so no equip call); `drone_skins`, `drone_mods` and `drones.applied_*` updated from the `item_bound` and `equipped` events; `users.points` set from `ft_balance_of`.
   The dashboard panel shows the step and the explorer link, calls again on 202 (at once after a step, after 3 s while busy or pending) and reloads when done. The 4-step onboarding tour stays.

## 14. Threat model

Assets: items, Volts, treasury, settlement authority, player keys, upgrade authority. Mitigations: scoped keys (4.1); encrypted custody; `seq` idempotency; commit-reveal with chain seed mix-in; `stats_hash` drift check; on-chain lock; team caps; escrow marketplace; owner methods only from the owner account; contract balance funded for storage; a single bootstrap per user (lease-claimed state machine, 12) and demo-account limits in the database (per IP, and a lifetime `DEMO_ACCOUNT_CAP`); one chain call in flight per player (action lease) and 30 mutations per player per minute (`rate_limits`); idempotent actions by client `actionId`; Origin check; security headers; secret scanning. Linked wallets (4.4): `withdraw` can only send a player's assets to that player's linked wallet, and once linked only that wallet can change the link, so a leaked ops key cannot redirect assets of a linked player (a play key has no path at all: `withdraw` and `unlink_wallet` are not in its method list and `unlink_wallet` needs 1 yocto). This does not cover a compromised server: it holds each player's admin full-access key (4.1) and the key that opens it, and could move assets with `nft_transfer` and `ft_transfer` directly. The first link is the weak point the contract cannot check: it trusts the server's session and NEP-413 signature check, so a leaked ops key or compromised server can link its own wallet to a player that has no link and then withdraw that player's assets. Each challenge is single use, bound to the session user, expires in 5 minutes (a claimed one included: past that, it can only confirm a link already on chain) and names the player's account; the signature must come from a full-access key on the wallet's account. The contract pays one Volts registration per link and a wallet can reclaim it with `storage_unregister`, so `POST /api/wallet/challenge` is capped at 10 per user per hour. NEAR Connect runs wallet code in sandboxed iframes (`sandbox=\"allow-scripts\"`, opaque origin, no access to cookies, the session or the page) loaded from its manifest; the manifest and executors are third-party code the app does not pin, so `/wallet` has its own Content-Security-Policy with exact origins (8).
