# Hyperdrome

Hyperdrome is an idle drone-racing strategy game on the NEAR testnet. You tune a drone (stat points, a mod, a skin), and every 3 minutes the scheduler races it 1v1 against a drone of a similar level and rating, with a 2-minute window to change your mod before the race locks. One contract, `game.hyperdrome.testnet`, holds the drones, skins and mods (NEP-171), the Volts currency (NEP-141), the marketplace, the packs and the race settlement, and it creates a NEAR account for every player and AI team. The problem it addresses: in most web games the server decides every outcome and owns every item. Here each race's seed hash is on chain before the race, the contract checks each result against the drones' on-chain state, anyone can replay a race from public data, and a player's items are tokens in their own NEAR account that they can withdraw to a wallet. Players sign in with Google or Play Demo and need no wallet and no gas.

- Live: https://hyperdrome-near.vercel.app (testnet only; no mainnet deployment)
- Contract: [game.hyperdrome.testnet on NearBlocks](https://testnet.nearblocks.io/address/game.hyperdrome.testnet)
- Tracks entered: games, nfts, security, agents (section 4)

## 2. Run it without our keys

Each command below was run from a fresh clone of this repository on 2026-11-09, in a shell with no environment variables of ours, and gave the result shown.

Verify a race from public data only: Node 24 ([.nvmrc](.nvmrc)), no database, no key.

```sh
npm ci
npm run verify:race -- <race id>   # any settled race; ids are listed at https://hyperdrome-near.vercel.app/api/races
```

It reads the race from `GET /api/races/<id>` and its `commit_batch` and `settle_batch` transactions from a public NEAR testnet RPC, then runs the same 8 checks as the Verify button with the same code ([scripts/verify-race.mjs](scripts/verify-race.mjs), [lib/client/race-verify.js](lib/client/race-verify.js)). It prints one line per check, ends with "All 8 checks passed." and exits 0; a check that fails prints `FAIL` and exits 1. `--base <url>` points it at another deployment.

The app's test suite, against a local Postgres as CI does (CI uses the `postgres:17` image; this was run with Postgres 16, whose `initdb`, `pg_ctl` and `createdb` must be on `PATH`):

```sh
npm ci
initdb -D tmp/pg -U ci --auth=trust
pg_ctl -D tmp/pg -o "-p 54329 -c unix_socket_directories=''" -l tmp/pg.log -w start
createdb -h 127.0.0.1 -p 54329 -U ci ci
DATABASE_URL=postgresql://ci@127.0.0.1:54329/ci npm run db:migrate
DATABASE_URL=postgresql://ci@127.0.0.1:54329/ci npm test   # 43 files passed, 1 skipped; 328 tests passed, 1 skipped
pg_ctl -D tmp/pg stop
```

The tests use the in-memory chain adapter and the real Postgres. The skipped file is the testnet integration test, which runs only with `NEAR_TESTNET_INTEGRATION` set and keys.

CI installs it with the release installer in [.github/workflows/ci.yml](.github/workflows/ci.yml) ("Install cargo-near 0.22.0"); on the machine that ran the clean-clone check it was already installed, so that step was not re-run there.

## 4. Tracks entered

- games. A game whose economy runs on chain: Volts are minted by race settlement and burned by upgrades, packs, capsules and vendor drones; the marketplace trades tokens for Volts with escrow and a 10% fee; four AI teams spend and trade in the same economy under on-chain caps; `/economy` shows the Volt supply, minted and burned, and each team's moves. Race results can be checked against the chain by anyone.
- nfts. Drones, skins and mods are NEP-171 tokens whose on-chain state changes through play: stats, level, XP, ELO and the items bound to them. The transfer rules are the game's rules (a bound item moves only with its drone), and a player can withdraw them to their own wallet.
- security. The custody model limits what each held key can do: scoped function-call keys, spend caps checked by the contract, withdrawals only to a wallet the player linked by signature, and the stats-hash check at settlement. An attack demo sends real transactions with a team-like test key treated as stolen and records which ones the contract or the protocol refuses ([docs/security-demo.md](docs/security-demo.md)). There is no AI model in the defense: it is key scope and contract checks.
- agents. Four AI teams act on their own every 3 minutes with their own scoped keys, under per-transaction and per-day spend caps the contract enforces, and every action is recorded with the reason for it. The teams are rule-based, with no LLM, and they do not negotiate with each other.

### security, the file map

Custody model ([SPEC.md](SPEC.md) 4.1): players sign in with Google or Play Demo and hold no key. The server holds each player's keys, so the design limits what a held key can do.

Attack demo: [docs/security-demo.md](docs/security-demo.md), written by `npm run attack:demo` ([scripts/attack-demo.mjs](scripts/attack-demo.mjs)). The AI teams are rule-based, so the demo assumes the worst case: an agent whose play key is stolen or whose logic is hijacked. It uses a test fixture built like a team, `testrogueagent.game.hyperdrome.testnet`, with caps of 500 Volts per transaction and 1,000 per day, never one of the four live teams. Each attempt is a real testnet transaction where the chain accepts one. A spend over the per-transaction cap and a spend past the daily cap are refused by the contract (`cap exceeded`). `ft_transfer`, `nft_transfer`, `mint_volts`, `set_team_budget`, an attached deposit and a NEAR transfer are refused by the protocol before any block. A normal `equip` with the same key succeeds.

When a key's gas runs out, the protocol refuses its next transaction (`NotEnoughAllowance`), and nothing partial lands. The first link is the one step the contract cannot check: it trusts the server's session and signature check.

## 7. How a race works

1. Commit. The tick for slot `S = floor(unix_seconds / 180)` pairs the active drones the chain reports as free, draws a track, weather and time of day per race, and generates a 32-byte seed. The seed is stored sealed (AES-256-GCM) before anything is sent; only `sha256(seed)` goes on chain with the matchups in `commit_batch`. [services/batch.service.js](services/batch.service.js), [lib/game-engine/matchmaking.js](lib/game-engine/matchmaking.js), `commit_batch` in [settlement.rs](contracts/hyperdrome/src/settlement.rs).
2. Strategy window and lock. For 120 seconds after the commit's block time the owner can `equip` and `allocate_stats`. From then until the batch settles, those two calls and `nft_transfer` panic `locked`; `bind` still binds an item and skips its auto-equip (`bind` in [player.rs](contracts/hyperdrome/src/player.rs)). The rule is the contract's: `STRATEGY_WINDOW_MS` in [constants/mod.rs](contracts/hyperdrome/src/constants/mod.rs), `is_locked_at` in [math.rs](contracts/hyperdrome/src/math.rs), sandbox test `locked_drones_refuse_player_moves_until_settled` in [tests/settlement.rs](contracts/hyperdrome/tests/settlement.rs).
3. Engine. In the next slot the server reads each drone's on-chain stats and equipped items (the state the lock froze), stores that snapshot, and runs `simulateRace`. All randomness comes from xoshiro128\*\* seeded with `sha256(seed ++ "<batch>:<index>")`, so the same seed and snapshots give the same winner, times and log. [lib/game-engine/race-simulator.js](lib/game-engine/race-simulator.js), [prng.js](lib/game-engine/prng.js), [mods.js](lib/game-engine/mods.js); 1,000 identical runs and a golden set of 20 races in [tests/engine/race-simulator.test.js](tests/engine/race-simulator.test.js) and [tests/golden/races.json](tests/golden/races.json).
4. Settlement. `settle_batch(batch_id, seed, from, results)` is sent in chunks of 40 races. The contract checks `sha256(seed)` against the committed hash (`bad seed`), each result against its committed matchup (`bad chunk`), and each drone's `stats_hash` against its current on-chain state (`state drift`). It then computes the payouts, the ELO change (a fixed-point table), XP and level-ups from its own constants and the reported result, mints the Volts in one `ft_mint` event and emits `batch_settled`. The server supplies each race's winner and two times and no reward amount; the times decide only the dominance bonus of 0, 2 or 5 Volts. [services/settle.service.js](services/settle.service.js), [settlement.rs](contracts/hyperdrome/src/settlement.rs), [math.rs](contracts/hyperdrome/src/math.rs), [tests/settlement.rs](contracts/hyperdrome/tests/settlement.rs). A batch that cannot settle is aborted with `abort_batch`, which unlocks its drones and pays nothing ([example](https://testnet.nearblocks.io/txns/AC7UXVCFwesAkvkTU2SdJkyb2FaZXpzTGNZ9z77ktKL5)).
5. Verify. Once a race is settled, `GET /api/races/<id>` publishes its seed, snapshots and log, and `GET /api/races/<id>/verify` replays it on the server and compares winner, both times and the log. [services/race-schedule.service.js](services/race-schedule.service.js) (`verifyRace`), [services/race-replay.js](services/race-replay.js). The published seed can be checked against the chain: for the race in section 1 the seed `8d2535cde0c71a39b4a510fc5636927042569dfd162bce8238d109811fd3b7a0` hashes to `4e62153d815dda606dc7efd99d54da111be7e8c114da3669b639c880bdbe7d9b`, the `seed_hash` that `get_batch(9966119)` returns. The simulator and its imports use no Node module (the SHA-256 is [lib/game-engine/sha256.js](lib/game-engine/sha256.js)). The Verify button on the race page and `npm run verify:race` (sections 1 and 2) run the stronger check: they read the commit and settle transactions from a public RPC themselves, so they do not rely on this route.

The scheduler that drives this is one HTTP route, `POST /api/races/run`, guarded by `CRON_SECRET` and by a unique `cron_ticks(slot)` row, so a doubled call does nothing ([services/scheduler.service.js](services/scheduler.service.js), [docs/runbooks/deploy.md](docs/runbooks/deploy.md)).

## 8. AI teams

Each tick, after the batch is committed, each team takes at most one action (one transaction, or two for a capsule), the first of these that applies: (a) equip the bound mod with the best fit for the race it was just matched into; (b) bind an unbound mod that beats the drone's best bound one; (c) allocate stat points along its persona weights; (d) open a starter mod capsule while it holds fewer than 6 unbound mods; (e) with 3 or more unbound mods, list the one that fits its races worst at 1.2x its rarity base price; (f) buy a listed mod whose fit beats the drone's best bound mod by 2 or more, at or under 0.8x its rarity base price. The team never plans to spend below a 5,000 Volt reserve.

The spend limits are the contract's, not the runner's: 5,000 Volts per transaction and 15,000 per day, checked in `charge_team_cap` on every debit a team's play key can make, and a team with no budget row can spend nothing. `get_team` returns the caps and the day's spend.

Every action a team sends since 2026-11-10 is recorded with a one-sentence reason built from the numbers its rule used (`explainPlan` in [lib/teams/explain.js](lib/teams/explain.js)) and shown with its transaction on https://hyperdrome-near.vercel.app/economy; `GET /api/economy` serves the same record.
